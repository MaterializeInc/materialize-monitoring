    Storing Logs#

    Loki keeps all durable log data in a single object storage backend, maintained by the Loki Compactor. This page covers where the gateway writes logs, the storage layout, the index, retention, and disaster recovery. See the logging architecture for how storage relates to the ingesters that write it and the queriers that read it.

    Where the gateway writes logs#

    The gateway writes processed logs to each destination in pipeline.destinations. The map holds one entry by default, loki, which writes to the bundled Loki. Each entry has its own components and its own queue.

    An entry’s type sets how the gateway writes to it:

    loki
    Pushes logs through loki.write, labeled with the entry’s name.
    otlp
    Sends logs, metrics, or both over one OTLP connection, through components labeled dest_<name>. A signal is on when its block is present.
    s3
    Archives logs as objects in an S3 bucket, through components labeled dest_<name>. See Archive logs to write-once storage.

    To write logs somewhere else as well, add an entry. The following example adds an external Loki that never slows down delivery to the bundled one:

    pipeline:
  destinations:
    archive:
      type: loki
      url: https://logs.example.com/loki/api/v1/push
      authType: bearer
      queue:
        capacity: 64MiB
        blockOnOverflow: false

    The following example sends logs to an OTLP backend that takes only logs, on that signal’s own endpoint:

    pipeline:
  destinations:
    opensearch:
      type: otlp
      url: http://data-prepper.logging.svc:21890
      logs:
        url: http://data-prepper.logging.svc:21892/v1/logs

    An otlp entry with a metrics block also receives metrics, filtered to its own metrics.minMetricImportance, over the same connection and credentials. Over gRPC, set protocol: grpc and write url as host:port; gRPC serves every signal on one endpoint.

    To authenticate to a destination with a client certificate, put the certificate and key in a Secret named mzmon-alloy-gateway-destination-tls in the gateway’s namespace. The gateway mounts it at /etc/mzmon/destination-tls, so set the destination’s tls.certFile and tls.keyFile to files there. Until the Secret exists, the mount is empty and a destination that names a file in it fails to load.

    To stop writing to the bundled Loki, set pipeline.destinations.loki.enabled to false. For every field, see pipeline.destinations in the values reference.

    Reduce what one destination receives#

    A destination can receive a reduced copy of the logs while every other destination keeps everything. Set any of the following fields in the destination’s logs block:

    FieldWhat it does
    selectorKeeps only entries matching a LogQL stream selector, such as {namespace=~"environment-.+"}. Line filters are allowed after it.
    minLevelDrops entries below a level: TRACE, DEBUG, INFO, WARN, ERROR, or CRITICAL.
    keepUnknownSet to false to drop entries with an UNKNOWN level, which minLevel keeps. The gateway gives a panic the level CRITICAL, so a level floor never drops one. Defaults to true.
    sampleRateKeeps a fraction of entries, above 0 and at most 1.
    rateLimitDrops entries above rate lines per second, allowing bursts of burst whole lines. burst defaults to rate, rounded up, and can be lower than it.

    The gateway applies them in that order, in a loki.process component of the destination’s own, loki.process "dest_<name>". Each drop is counted in loki_process_dropped_lines_total, with reason set to destination_selector, destination_level, destination_sampling, or ratelimit_drop_stage.

    The following example sends only warnings and above from environment namespaces, at most 500 lines per second:

    pipeline:
  destinations:
    controlPlane:
      type: otlp
      url: https://ingest.example.com
      logs:
        selector: '{namespace=~"environment-.+"}'
        minLevel: WARN
        rateLimit:
          rate: 500

    To send a destination no logs at all, set logs.enabled to false rather than a sample rate of 0.

    Keep one destination from holding back another#

    The gateway hands every log entry to each destination in turn. A destination that blocks when its queue is full makes the gateway wait for room, and while it’s stalled, no other destination receives anything either.

    The types differ in their default:

    • A loki destination blocks. Set queue.blockOnOverflow: false on every loki destination except the one whose copy must be complete. It then drops entries when its queue is full, and counts them in loki_write_dropped_entries_total{reason="queue_is_full"}. queue.capacity sets how far it can fall behind before it drops.
    • Every other type drops. It counts what it drops in otelcol_exporter_enqueue_failed_log_records_total, and queue.queueSize sets how many requests it holds.

    The render warns when more than one log destination blocks.

    pipeline.logging.gateway.destination.loki is deprecated. Keys you still set there apply to pipeline.destinations.loki, and the render warns. Move each key across, so pipeline.logging.gateway.destination.loki.url becomes pipeline.destinations.loki.url.

    Archive logs to write-once storage#

    An s3 destination writes a copy of selected logs to an S3 bucket. With S3 Object Lock in compliance mode on that bucket, no one can delete or overwrite the objects until their retention period ends, which is what a compliance archive needs. The archive is separate from Loki’s own bucket, so Loki’s compactor and retention keep working on the operational copy.

    The following example archives warnings and above from Materialize’s environments:

    pipeline:
  destinations:
    worm:
      type: s3
      bucket: example-audit-logs
      region: us-east-1
      prefix: mzmon/audit
      logs:
        selector: '{namespace=~"environment-.+"}'
        minLevel: WARN

    Choose what the archive receives with the reduction fields. Without them, it receives every log line the gateway processes.

    profiles/s3-worm.values.yaml sets up this destination with a bounded queue. For what to decide before you archive, such as the retention mode and what to keep out, see Log compliance.

    Prepare the bucket#

    The chart writes objects; it can’t create the bucket or verify its lock. Turn Object Lock on when you create the bucket, and set a default retention in compliance mode:

    aws s3api create-bucket --bucket example-audit-logs --object-lock-enabled-for-bucket
aws s3api put-object-lock-configuration --bucket example-audit-logs \
  --object-lock-configuration '{"ObjectLockEnabled":"Enabled","Rule":{"DefaultRetention":{"Mode":"COMPLIANCE","Days":365}}}'

    In compliance mode, no user, the root account included, can shorten the retention or delete an object before it ends. Test with a short retention in a scratch bucket first.

    Every upload carries a checksum, which S3 requires for an upload into a bucket with Object Lock.

    Grant the gateway write access#

    The gateway authenticates with its ambient AWS identity:

    • On EKS, annotate the gateway’s ServiceAccount with an IAM role (IRSA), through alloy-gateway.serviceAccount.annotations.
    • Elsewhere, put AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY in the gateway Secret.

    The identity needs s3:PutObject on the bucket and prefix, and nothing else. To write to a bucket in another account, set roleArn to a role there that the gateway’s identity can assume.

    For an S3-compatible store, set url to its endpoint and forcePathStyle: true. An http:// URL turns TLS off for that endpoint.

    What lands in the bucket#

    The exporter writes one object per batch, gzip-compressed, at <prefix>/year=YYYY/month=MM/day=DD/hour=HH/minute=MM/logs_<uuid>.json.gz. The key ends in a UUIDv7, which in practice no two objects share. A UUIDv7 starts with a millisecond timestamp, so keys within a partition sort by when they were written. The time partitions are UTC unless partitionTimezone says otherwise. A batch closes after batch.timeout (default 1m) or batch.size records (default 8192), whichever comes first, so a quiet minute writes no object.

    Each object is OTLP JSON. A record’s body is the log line, and its stream labels, such as namespace and level, are attributes. marshaler: body writes the lines alone, without labels.

    When the archive drops a record#

    Like the other OTLP-family destinations, an s3 destination drops records rather than holding back the gateway’s other destinations. It drops a record when its queue is full, or when S3 refuses it after retries. Either way, the log-archive-drops alert fires, and the record is missing from the archive.

    Each batch gets about five minutes of retries, so an S3 outage longer than that drops records. The batch in progress and the queue live in the gateway’s memory, so a gateway that’s killed, for example by the OOM killer, loses them uncounted. queue.queueSize caps how many batches wait in memory. Alloy’s default, 1000, can outgrow the gateway’s memory limit on a busy install.

    Object storage#

    Loki is a black box over an S3-style object store. The supported backends are S3-compatible storage (AWS S3, MinIO, Ceph, R2, …), Google Cloud Storage, and Azure Blob Storage. For integration testing, Loki instead uses a local filesystem store in single-binary mode — no object storage required.

    A single bucket holds everything, separated by prefix:

    PrefixContents
    /loki/chunkscompressed log chunks and the TSDB index
    /loki/rulerLoki Ruler rule definitions

    Prefer granting access through cloud workload identity (IRSA on AWS, Workload Identity on GKE, Azure Workload Identity) so no long-lived credentials live in the cluster. Manually configured credentials are supported as a documented escape hatch for environments where workload identity is unavailable.

    Selecting the backend#

    The chart’s defaults are S3-shaped, so an AWS install only has to supply bucket names. Every other backend has to be named in three places, and all three have to agree:

    ValueRead by
    loki.loki.storage.object_store.typethe chunk and index clients, and the Ruler store
    loki.loki.schemaConfig.configs[].object_storethe chunk client for that schema period
    loki.loki.compactor.delete_request_storethe compactor’s delete-request store

    None of these fail softly. The client is chosen by name and then validated against a configuration that was never populated, so the component that reads a stale value crash-loops with create bucket: no s3 endpoint in config file. The schema period is the one that hurts most — it selects the chunk client, so every ingester fails at startup.

    There is a fourth, loki.loki.storage.type, which is the pre-Thanos selector. Loki ignores it while use_thanos_objstore is on and logs that it is doing so, so a stale value is misleading rather than broken — set it anyway, so the rendered configuration does not contain a contradictory store.

    The chart validates the set at render time and refuses to install a mismatched config, naming the value to fix. The exception is a schema period that is not the newest: those are allowed to name the previous backend, because that is what an append-only backend migration looks like.

    charts/materialize-monitoring/profiles/gcp-example.values.yaml and azure-example.values.yaml set all four for their backend and are the shortest path to a correct non-AWS config. The Azure profile carries more than the other two, because Entra Workload ID needs a pod label the Thanos chart cannot render — read its header before copying. The Terraform module derives all four from object_storage.cloud, so there is nothing to keep in sync there.

    Granting object-storage access (workload identity)#

    On every managed cloud the recommended way to give Loki access to its bucket is workload identity — no static keys in the cluster. The shape is the same across providers: a Loki pod runs as a Kubernetes ServiceAccount annotated to reference a cloud identity → the platform projects a signed token into the pod → that token is exchanged for short-lived cloud credentials → Loki uses them against the object store. Only the binding mechanism differs. Pick your provider:

    IRSA (IAM Roles for Service Accounts). Chain: ServiceAccount annotated with a role ARN → EKS projects an OIDC token → the SDK calls STS AssumeRoleWithWebIdentity → temporary credentials → S3. Requires the cluster’s OIDC provider registered in IAM (one-time).

    Trust policy — scope :sub to the exact namespace and ServiceAccount Loki runs as: ServiceAccount loki (a deterministic fullnameOverride) in the release namespace (recommended monitoring). Scope it to Loki’s, not another workload’s. For several component ServiceAccounts, use StringLike with a * suffix.

    {
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::<account-id>:oidc-provider/oidc.eks.<region>.amazonaws.com/id/<oidc-id>" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": { "StringEquals": {
      "oidc.eks.<region>.amazonaws.com/id/<oidc-id>:aud": "sts.amazonaws.com",
      "oidc.eks.<region>.amazonaws.com/id/<oidc-id>:sub": "system:serviceaccount:monitoring:loki"
    }}
  }]
}

    The default assumes the release is installed into monitoring. Under split namespaces, the :sub is system:serviceaccount:loki:loki instead.

    A trust policy scoped to the wrong namespace/ServiceAccount is what produces STS: AssumeRoleWithWebIdentity … 403 AccessDenied.

    Permissions policy — least-privilege to the single bucket + /loki/*. DeleteObject is required (compactor retention/compaction and the delete-requests store).

    {
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": ["s3:ListBucket"], "Resource": ["arn:aws:s3:::<bucket>"],
      "Condition": { "StringLike": { "s3:prefix": ["loki/*"] } } },
    { "Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": ["arn:aws:s3:::<bucket>/loki/*"] }
  ]
}

    ServiceAccount — annotate through chart values; the EKS webhook then injects AWS_ROLE_ARN / AWS_WEB_IDENTITY_TOKEN_FILE.

    loki:
  serviceAccount:
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::<account-id>:role/<loki-role>

    GKE Workload Identity. Chain: the Loki ServiceAccount is annotated with a Google service account (GSA) → GKE exchanges the pod’s token for that GSA’s credentials → GCS. Requires Workload Identity enabled on the cluster and node pool. Below, <gsa> is the GSA; [<namespace>/loki] is the Kubernetes ServiceAccount (KSA).

    1. Grant the GSA object access on the bucket:

      gcloud storage buckets add-iam-policy-binding gs://<bucket> \
  --member="serviceAccount:<gsa>@<project>.iam.gserviceaccount.com" \
  --role="roles/storage.objectAdmin"

    2. Bind the GSA’s IAM policy so the Loki KSA may impersonate it — the KSA must match Loki’s namespace/ServiceAccount:

      gcloud iam service-accounts add-iam-policy-binding <gsa>@<project>.iam.gserviceaccount.com \
  --role="roles/iam.workloadIdentityUser" \
  --member="serviceAccount:<project>.svc.id.goog[monitoring/loki]"

      The default assumes the release is installed into monitoring. Under split namespaces, use --member="serviceAccount:<project>.svc.id.goog[loki/loki]" here.

    3. Annotate the ServiceAccount — and set the GCS backend in all four places from Selecting the backend, which the annotation alone does not do:

      loki:
  serviceAccount:
    annotations:
      iam.gke.io/gcp-service-account: <gsa>@<project>.iam.gserviceaccount.com

    Microsoft Entra Workload ID. Chain: ServiceAccount annotated with a managed-identity client ID → AKS projects a token → exchanged with Entra for the identity’s credentials → Azure Blob. Requires the OIDC issuer + workload identity enabled on the cluster.

    1. Grant the user-assigned managed identity Storage Blob Data Contributor on the storage account (or container scope).

    2. Create a federated identity credential on that identity — subject must match Loki’s namespace/ServiceAccount:

      • issuer = the AKS cluster’s OIDC issuer URL
      • subject = system:serviceaccount:monitoring:loki
      • audience = api://AzureADTokenExchange

      The default assumes the release is installed into monitoring. Under split namespaces, the subject is system:serviceaccount:loki:loki instead.

    3. Annotate the ServiceAccount, label the pods so the webhook injects the token, and set the Azure backend in all four places from Selecting the backend:

      loki:
  serviceAccount:
    annotations:
      azure.workload.identity/client-id: <client-id>
  # The workload-identity webhook only acts on pods carrying this label;
  # apply it via the chart's pod-label values for the Loki components.
  podLabels:
    azure.workload.identity/use: "true"

    The token exchange and the object store are both 443 hops to your cloud’s identity and storage endpoints (AWS: STS + S3; GCP: sts.googleapis.com/oauth2.googleapis.com + GCS; Azure: login.microsoftonline.com + Blob). If you enable the Loki NetworkPolicy you must allow that egress (networkPolicy.externalStorage), or the credential fetch fails — a blocked egress hangs the compactor at startup (a silent connect timeout), while an allowed egress with a bad binding returns a fast auth error. See Operating > Production Best Practices.

    Alternatives. EKS Pod Identity is a newer AWS alternative to IRSA (a pod-identity association, no oidc-provider to manage). Static keys / connection strings are the last-resort escape hatch on any cloud — supply them as a Secret consumed by reference, for environments without workload identity.

    Verifying. Confirm the ServiceAccount carries the provider annotation and the pod has the injected identity env/token, then split the two failure modes: a failure during the token exchange (403/AccessDenied on AssumeRoleWithWebIdentity, or the equivalent GCP/Azure exchange error) is a binding/trust-scope problem — usually a namespace/ServiceAccount subject mismatch; an authorization error on the storage operation itself, after the exchange succeeds, is a permissions problem on the bucket/container.

    Chunks and the index#

    Two kinds of data live in the bucket:

    • Chunks — the compressed log lines themselves, flushed from ingesters in batches.
    • The index — the map from stream labels to the chunks that contain them, written in the TSDB index format (schema v13).

    Because Loki indexes only labels, the index stays small relative to the log volume — the chunks dominate storage. Structured metadata is stored with the chunks, queryable but not part of the label index.

    The schema is configured in append-only periods with a future start date; a period that is already in use can never be changed retroactively. Plan schema changes (for example a future index-format bump) as a new period with a from date ahead of now — never by editing a past period.

    Compaction#

    The Loki Compactor merges the many small index files produced by individual ingesters into a single compacted index per tenant per day. This keeps reads efficient as volume grows. The compactor is a singleton — exactly one instance coordinates against the shared bucket.

    Retention#

    Retention is enforced by the compactor, not by the object store’s own lifecycle rules.

    • A global retention period sets how long logs are kept before deletion.
    • Tiered (per-stream) retention lets different log streams keep data for different lengths of time — for example, keeping ERROR and audit-relevant streams far longer than high-volume INFO chatter. This is a primary cost lever at fleet scale.
    • The deletion API processes targeted deletes (for example, compliance “right to be forgotten” requests) outside the normal retention schedule.

    Scaling#

    • Ingesters run ephemerally (node-local emptyDir, no PVC); durability comes from the replication factor of 3, so you run at least three. Scale past three on memory / stream cardinality, not bytes.
    • Object storage scales on its own — there is no capacity to provision, only cost and retention to manage.
    • Scaling the read side (queriers, frontend) is independent and covered in Querying.

    Ingester rollouts happen one at a time (guarded by a PodDisruptionBudget). flush-on-shutdown is best-effort — a truncated flush is covered by the other replicas, so durability does not depend on a graceful stop. See the ingester notes and Operating > Upgrading.

    Disaster recovery#

    Loki has no native snapshot mechanism — recovery is a property of the object store, not a Loki feature:

    • Durability and versioning. Chunks are immutable once written; enabling object versioning protects against accidental overwrite or deletion.
    • Cross-region replication. Replicating the bucket to a second region gives you a recovery point if the primary region is lost.
    • Tamper evidence. Object Lock / WORM (compliance mode) makes stored logs immutable for a fixed window — important when logs must serve as evidence in a security or audit event. Locking Loki’s own bucket also stops its compactor and retention from deleting chunks, so for a write-once copy, archive logs to a separate bucket.
    • Restore. Recovery is “repoint Loki at the bucket.” The WAL is ephemeral and the index is rebuilt from object storage, so there is no separate database to restore.

    During a security or audit event, the log store’s guarantees come from these object-store features. Freeze the relevant bucket (or a replicated copy) to preserve logs before retention or deletion can act on them.
