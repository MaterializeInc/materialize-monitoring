    Datadog dashboards from the query registry#

    agentClaude Opus 5.5
    authorHeather Lapointe
    lastmod2026-10-21 00:00:00 +0000 UTC
    publishdate2026-10-20 00:00:00 +0000 UTC
    statusDraft

    This doc proposes how materialize-monitoring builds a Datadog dashboard set from the query registry that the Grafana dashboards already read. It owes DEP-115, whose description predates the Rust dashboards rewrite in DEP-222 and names paths that no longer exist. In this doc, “you” is a contributor to this repository or an agent working for one.

    The central claim is that the Datadog set adds nothing to the install. The dashboards are JSON files that an operator downloads from the docs site and imports into Datadog. Where a panel shows names rather than ids, it gets them by formula arithmetic in Datadog, against the _info series the gateway already collects. What the set needs from the stack is a change to which series the gateway sends and how they’re labeled, and no new component.

    Goals#

    The goals come from the following stakeholders:

    • Operators who send metrics to Datadog through the gateway’s Datadog destination.
    • Field Engineering and support, who read those dashboards alongside a customer.
    • Maintainers of this repository, who keep two dashboard backends in step.

    Functional requirements are framed as value-first user stories. Priority tags (Must / Should / Could) are relative to the first shipped version.

    • [Must] As an operator who uses Datadog, I want to download a Materialize dashboard set from the docs and import it, so that I don’t rebuild the Grafana dashboards by hand.
    • [Must] As an operator with several environments in one Datadog organization, I want every panel scoped to one environment at a time, so that two environments’ series never merge into one line.
    • [Must] As a maintainer, I want a Datadog panel and its Grafana counterpart to render from one registry entry, so that the two backends can’t disagree about what a number means.
    • [Should] As an operator, I want clusters, replicas, and objects shown by name, so that a panel answers “which one” without a lookup in SQL.
    • [Should] As an operator, I want a rename to change the name a panel shows without changing the series underneath, so that a rename doesn’t reset rates or history.
    • [Should] As a maintainer, I want a change in Datadog’s API to fail CI rather than a customer’s import, so that published dashboard JSON doesn’t age out of compatibility.
    • [Should] As a maintainer, I want a panel added to one set to fail CI until the other set has it or the gap is listed, so that the two sets don’t drift apart unnoticed.
    • [Could] As an operator who uses Terraform, I want to manage the downloaded dashboards as Terraform resources, so that I manage them the way I manage the rest of the install.
    • [Could] As an operator, I want to pick a cluster by name in a dashboard variable, so that I don’t have to know its id.

    Technical BLUF#

    • The dashboards ship as downloadable JSON on the docs site, never in a chart. The docs site’s download-dashboards shortcode already has a Datadog row that reads docs/assets/dashboards/datadog/NAME.json. The Grafana dashboards are the only ones that live in the cluster.
    • The backend builds on the models in datadog-api-client, Datadog’s official Rust client. The crate is generated from Datadog’s OpenAPI spec. The workspace already builds its HTTP stack, so the added cost is compiling the models.
    • Names, where a panel shows them, come from formula arithmetic. A formula such as a * (b * 0 + 1), with b an _info query grouped by the id and the name, keeps a’s values and carries b’s extra tags. It’s Datadog’s counterpart to * on (id) group_left (name), and it’s an inner join, so a series with no _info row drops out of the panel.
    • The join matches on tag names, so both sides have to spell the id and the environment the same way. Datadog can’t rename a tag inside a query. The relabel rules from the label-vocabulary design give both sides the canonical names, and names in Datadog wait on them.
    • The _info series have to reach Datadog. Two of the three aren’t in the metric tier list today, so the Datadog destination’s default tier drops them. Each _info series that does reach Datadog is a custom metric.
    • Reference tables stay an option, outside the first version. They solve names without sending _info series, at the price of a sync component, an application key, and a join shape that Datadog doesn’t publish for dashboards.
    • Thanos is always there. The tenant-scoped read path makes a PromQL endpoint part of every deployment, Datadog destination or not. That keeps pre-joined recording rules available as an option too.
    • A parity ledger keeps the two sets in step. Each backend records a manifest of its panels, their registry queries, kinds, and units, and a test fails on any difference that isn’t listed with a reason. A shared panel layer follows only if the ledger shows the two backends repeating one list.

    Non-goals#

    • Installing dashboards from the cluster. No chart carries Datadog JSON, and nothing in the install calls Datadog’s dashboard API.
    • Reference tables in the first version. See Other ways to get names.
    • Datadog monitors. Alerting stays in the Prometheus rules and Alertmanager that this stack ships, as designed in Alerting in Self-Managed.
    • Collection through the Datadog Agent. The stack sends metrics through the gateway’s otelcol.exporter.datadog. The Agent’s OpenMetrics check can copy labels between metrics at scrape time, and this design doesn’t rely on it.
    • Parity with every Grafana dashboard in the first version. See Scope of the first set.
    • Datadog log dashboards. The Datadog destination forwards logs too, and their dashboards are a separate design.
    • The label vocabulary. A Label Vocabulary for Materialize Metrics owns label names and the environment key. This doc consumes its decisions.
    • The Google Cloud Monitoring and Honeycomb sets (DEP-217, DEP-218). They share the registry, and their join stories differ from Datadog’s.

    The following properties of this diagram carry the design.

    Nothing new runs in the install. The gateway’s labels and tier filter change, and no component is added.

    A dashboard reaches Datadog through a person, not through the cluster. An operator downloads it from the docs site and imports it, so the install holds no Datadog application key.

    The join happens in Datadog, when a panel’s query runs, over tags both series already carry. Names never go onto the data series, so a rename changes no series’ identity.

    The backend#

    Models from datadog-api-client#

    The Datadog backend lives in packages/dashboards/src/datadog/, beside grafana/, where packages/dashboards/src/lib.rs already expects a second backend. It builds dashboards from the models in datadog-api-client, Datadog’s official Rust client. The crate is generated from Datadog’s OpenAPI spec and licensed Apache-2.0, and its 0.38.0 release is from 2026-10-13. Its datadogV1::model module types the dashboard, its tabs and template variables, and each widget definition.

    The backend uses the models and not the client. The dependency is default-features = false, features = ["rustls-tls"]. reqwest isn’t optional in the crate, but mz-monitoring-build already builds reqwest 0.13 with rustls. The crate covers Datadog’s whole v1 and v2 API, so compiling its models is the largest cost of this choice.

    Queries come from the registry through QueryEngine::Datadog, the same way the Grafana backend renders PromQL. The output is plain dashboard JSON, one file per dashboard.

    What the spec doesn’t describe#

    Every model in the crate keeps the fields it doesn’t know in a flattened additional_properties map. Every oneOf union, including the widget query union FormulaAndFunctionQueryDefinition, has an UnparsedObject variant. A field or query type that the spec lacks therefore round-trips without a type.

    A dashboard exported from the Datadog UI can carry shapes the spec doesn’t describe. A table widget built in the UI’s table editor, for example, exports request_type: "table" with rows and columns, and metric queries with metric_name and filter. The backend emits the spec’s form of the same table instead: a metric query grouped with by {…}, its formulas, and response_format: "scalar".

    Generated models, considered#

    The alternative is the approach the Grafana backend takes. bin/gen-grafana-models.sh runs cargo typify over vendored JSON Schema documents, and generates only the packages the dashboards use. The dashboard part of Datadog’s OpenAPI spec could be vendored and generated the same way. The result would be smaller and model-only. It would also mean maintaining a normalization from OpenAPI 3.0 to JSON Schema, over a v1 spec with 1,249 schemas, which the crate’s maintainers already do. Generated models stay the fallback if the crate’s compile time becomes a problem.

    Delivery: a download from the docs site#

    make datadog-dashboards renders each dashboard to docs/assets/dashboards/datadog/NAME.json. The download-dashboards shortcode already lists a Datadog row for every dashboard, and offers the file as soon as it exists. An operator downloads the file and imports it into Datadog, through the UI or POST /api/v1/dashboard. An operator who uses Terraform can pass the same file to the Datadog provider’s datadog_dashboard_json resource.

    No chart carries the JSON. The Grafana dashboards are the only dashboards that live in the cluster. Helm stores each release, its chart files included, in a Kubernetes Secret, and a Secret can’t exceed 1 MiB. A Datadog set in a chart would spend that ceiling on files nothing in the cluster reads. The empty placeholder at charts/materialize-monitoring-dashboards/pre-rendered/dashboards/datadog/ is removed in this change for the same reason.

    The dashboards carry template variables for the environment and the Kubernetes cluster, defaulting to every value. Each panel groups by those tags as well as its own, so an organization with several environments sees one line per environment rather than a merged one.

    Names come from formula arithmetic#

    The arithmetic join#

    Datadog matches series by their tags when a formula combines two grouped metric queries. The repository’s Datadog Translations page records the behavior, and a join built in the Datadog UI on 2026-10-20 shows it working as a label join:

    a: sum:kube_pod_status_ready{*} by {pod,namespace}
b: sum:kube_pod_info{*} by {pod,namespace,node,pod_ip}
formula: a * (b * 0 + 1)

    b * 0 + 1 is 1 wherever b has a point, so the product keeps a’s values. The result carries b’s extra tags, node and pod_ip, the way * on (pod, namespace) group_left (node, pod_ip) would in PromQL. b can be hidden in the widget, because Datadog still evaluates a hidden query in the formulas that use it.

    For a Materialize panel, b is an _info query grouped by the environment’s tags, the id, and the name. The following example uses the canonical label names, which the join needs:

    a: max:mz_dataflow_wallclock_lag_seconds{$environment} by {cluster,environment_id,cluster_id,collection_id}
b: max:mz_object_info{$environment} by {cluster,environment_id,collection_id,object_name}
formula: a * (b * 0 + 1)

    The match is on every tag the two queries share, so a u1 in one environment matches only its own environment’s _info series. No composite key is needed.

    How the arithmetic join behaves#

    Datadog’s documentation doesn’t describe how a formula matches series between queries with different group-bys, as of 2026-10-20. The following table records what Datadog’s query API did on 2026-10-21, probed read-only with a test install’s Kubernetes metrics. The timeseries endpoint backs the timeseries widget, and the scalar endpoint backs the query value, table, and toplist widgets. Both endpoints behaved the same.

    BehaviorResult
    Group keys that differRejected with HTTP 400, “Series to be aligned must have group keys that match…”, unless one query’s group-by keys equal the other’s or are a subset of them
    Tags on the resultThe larger of the two group-by sets
    A left series with no match on the rightDropped. With b filtered to one namespace, 3 of a’s 174 series remained
    A left series that matches several right seriesOne result series per match. a grouped by namespace alone fanned out to the 174 (namespace, pod) series of b
    A right series with no point at a timestampNo point in the result. Every series with partial coverage over the window, 22 of them, went null exactly where b did
    A filter on a tag only the right side carriesFilters the result. With b filtered to one node, the result held that node’s 34 pods
    The join inside a formula that does its own arithmeticWorks. (a / c) * (b * 0 + 1) returned all 174 series
    Two formulas with different group keys in one tableTheir rows don’t line up. Each formula filled 174 of 348 rows

    The results settle the following rules for the design:

    • A mismatched id fails loudly. A query pair that spells the id differently is rejected rather than joined on the tags it shares, so a panel can’t show another cluster’s name.
    • The join is an inner join. A joined panel loses every series that has no _info row. A panel joins names only where its _info family covers every id its query returns, and otherwise shows ids.
    • A rename splits a series in two. The id matches the old name until the rename and the new name after it, and each result series is null outside its own name’s lifetime.
    • A name filter works. A dashboard variable on the _info query’s name tag narrows the panel to that name, which makes the [Could] story possible.
    • A table joins every column or none. Every formula in a table widget needs the same group keys, so a table that shows names joins each of its columns.
    • The _info query aggregates in space. Grouping b with max: collapses identical rows from two producers, such as two environmentd pods during a rollout.

    What the join needs from the series#

    The join needs the following from the series that reach Datadog:

    Matching tag names
    Datadog can’t rename a tag inside a query, so an id has to carry the same tag name on both sides. A pair that doesn’t is rejected with HTTP 400, so the mismatch shows up as an error rather than as wrong names. Today it doesn’t: mz_cluster_info names a cluster cluster_id where the series it names say instance_id, and mz_object_info says global_id where they say collection_id. The relabel rules in DEP-349 copy each alias to its canonical name in the shipped monitors, on both sides. Names in Datadog wait on them.
    The environment’s tags on both sides
    Both queries group by cluster and the environment’s id, so the match can’t cross environments. Until DEP-351 puts environment_id on the series, the environment’s tags are namespace and materialize_cloud_organization_name.
    cluster on the Datadog chain
    The Datadog chain doesn’t put cluster on series today. The prerequisite is to fill it from CLUSTER_NAME where it’s absent, as the remote-write external_labels and the Google Cloud chain already do. An organization that receives several Kubernetes clusters needs a distinct clusterName for each, and the Datadog dashboards page says so.
    The _info families at the destination’s tier
    Tier extraction treats the enrichment functions as the identity, so mz_object_info and mz_replica_info aren’t in the tier list. The fix is for extraction to count the _info family an enrichment function reads, at the importance of the query that reads it. Each _info series in Datadog is a custom metric, one per catalog object, cluster, or replica, and the Datadog dashboards page says so. The join is an inner join, so a panel joined to a family that doesn’t reach Datadog shows nothing at all.

    One enrichment declaration, two realizations#

    A registry query asks for names by attaching an enrichment function, such as mzObjectName or mzClusterName, to its template. The PromQL rendering context implements each function as a group_left join, through packages/mzmon-lib/src/query/enrich.rs. The extraction context, which builds the docs and the tier list, implements each function as the identity.

    The datadogQuery templates gain the same functions list. The Datadog rendering context implements each function as a hidden _info query and a factor on the panel’s formula. mzObjectName over collection_id, for example, adds b: max:mz_object_info{…} by {…,collection_id,object_name} and turns the formula F into (F) * (b * 0 + 1). A panel that shows names says so once, in its registry entry, and both backends follow it. Because the join drops unmatched series, the Datadog context renders a panel’s join only where its _info family covers every id the query returns.

    Other ways to get names#

    Reference tables#

    A reference table is a keyed table stored in Datadog. Reference Table Joins with Metrics add a table’s columns to a metric query’s result as tags, matching one tag of the query to the table’s key. They would give names without sending any _info series to Datadog.

    They’re outside the first version, for the following reasons:

    • One attribute, one key. A join matches one tag to one column, and a table has one primary key. Catalog ids repeat in every environment, so the key would be a composite tag, such as <cluster>/<environment_id>/<id>, built in the gateway for both the series and the rows.
    • A component in the install. Something has to keep the rows current. That would be a sync per install, writing rows through POST and DELETE /api/v2/reference-tables/tables/{id}/rows, which needs no CSV upload or bucket. It would read the _info series from Thanos, which every install has.
    • A Datadog application key in the cluster. The Reference Tables API needs one with reference_tables_write, which the metrics exporter doesn’t.
    • An unpublished shape. Datadog’s spec describes the join for monitors, in MonitorFormulaAndFunctionAggregateAugmentedQueryDefinition, and has no variant for it among the dashboard widget queries. The shape would have to come from a UI export.
    • Shared tables. A join names one table, so every install in an organization would write to the same tables, each deleting only its own rows.

    The arithmetic join drops series that have no _info row, and the monitor spec offers reference-table joins of type left, which keep them. Reference tables become worth their cost if too many panels fall back to ids for that reason, or if the custom metrics for the _info series cost too much.

    Pre-joined recording rules#

    The Thanos Ruler remote-writes its results to the gateway, and every install has Thanos, so a recording rule that joins names onto series would reach Datadog with no new component. This design doesn’t use it for the dashboards, for the following reasons:

    • A destination below the all tier drops recorded series until DEP-368 gives them a tier.
    • Both ruler replicas send every result. Datadog doesn’t deduplicate on ruler_replica, so each copy is a custom metric of its own.
    • A name on a series is part of the series’ identity. A rename ends one series and starts another, which is why the label-vocabulary design keeps names on _info metrics only.

    Scope of the first set#

    DEP-115 asks whether the first version is full parity with the Grafana set or a subset. This doc proposes a subset, starting with env-top. Its registry entries already carry Datadog templates, and the other dashboards link from it. Field Engineering sets the order after that, as DEP-115 recommends.

    The first set shows ids. Names are a Should, and they wait on the canonical labels from DEP-349, so each panel gains them when its labels match.

    The datadogQuery templates were written for completeness, and the PromQL is the tested half. Each panel’s Datadog query is checked against live data when it’s ported.

    Keeping the two sets in step#

    The registry already keeps the meaning of the two sets in step, because both backends name each query by its registry id. What can still drift is everything around those queries: which panels exist, where they sit, which queries each one reads, and what kind of panel each one is. This design checks that with a parity ledger now. It moves the panel list into a shared layer only if the ledger shows the two backends repeating it.

    A parity ledger over panel manifests#

    Each backend produces a manifest of every dashboard it renders. The manifest records the following for each panel, in section order:

    Slug
    The panel’s stable id. The Grafana builders already give every panel one, as in .panel("freshness-lag-by-cluster", …).
    Title
    The title the panel shows.
    Queries
    The registry ids the panel reads, with any argument that changes what they select, such as a split by replica or by worker.
    Kind
    A broad class of panel: time series, single value, table, or pie.
    Unit
    The unit of the panel’s values.
    Names
    Whether the panel joins names, and through which enrichment function.

    The builders record the manifest as they build each dashboard. Every Grafana query lookup already passes through Queries::bridge in packages/dashboards/src/grafana/queries.rs, which records the lookups that fail. Recording the lookups that succeed, against the panel being built, uses the same mechanism.

    A test compares each Datadog dashboard’s manifest with its Grafana counterpart’s. It fails when a panel is in one and not the other, or when the two disagree on a field, unless the difference is listed with its reason. The listed differences live in one place, as ALLOWED and ADDED_PANELS do in packages/dashboards/tests/env_top_parity.rs, which compared the Rust env-top with its earlier render the same way. Typical reasons are a log panel, a query with no datadogQuery yet, and a panel kind that Datadog has no counterpart for. A long list means the ledger has stopped describing the two sets, and the comparison stops being worth running.

    The ledger has the following further uses:

    • The Datadog dashboards page renders the listed differences as a table of Grafana panels without a Datadog counterpart, each with its reason.
    • A query that a Datadog panel needs and that has no datadogQuery fails the test until someone writes the template or lists the gap.

    The ledger doesn’t compare layout, sizes, colors, thresholds, legends, links, or transformations. Those belong to each format, and comparing them would mostly report noise.

    This design considered a structural comparison of the rendered JSON, and rejected it. Grafana’s grid, rows, field overrides, and transformations share almost nothing with Datadog’s layout, groups, formulas, and conditional formats. Comparing them would first mean normalizing both into a common shape, and that shape is the manifest, recovered from output after the builders have already discarded it.

    A shared panel layer, if the ledger shows duplication#

    This design also considered interlacing the two definitions now, with every panel builder rendering per backend, and rejected it. The Grafana set is the one that lives in the cluster, and it uses features Datadog has no counterpart for: conditional rows, transformations, data links, log panels, and Grafana-only variable types. Rendering every Grafana panel through a Datadog-aware builder would bring Datadog’s limits into each one. packages/dashboards/src/lib.rs also asks for shared structure to grow out of a second backend rather than be designed ahead of one.

    If the ledger shows the two backends restating the same panel list, that list moves into a backend-neutral layer. The layer holds what the manifest records: sections, slugs, titles, query ids, kinds, units, and name joins. Each backend renders from it, and keeps its presentation in its own code, keyed by slug. The ledger then reduces to one assertion: every shared panel renders in both backends, or is listed as skipped.

    Catching API drift#

    DEP-115 asks for a CI job that runs the SDK at its latest version and surfaces drift. Renovate already proposes crate bumps. The dashboards workflow already fails when a fresh render differs from the committed output. Extending that check to the Datadog output makes a crate bump that changes the rendered JSON show its diff in Renovate’s own pull request.

    A render can’t prove that Datadog accepts the JSON. Datadog’s v1 API has no validate-only dashboard endpoint, so proving acceptance means creating each dashboard in a test organization, reading it back, and deleting it. The same job runs each widget’s queries through the query API, which rejects a mismatched join with HTTP 400. That check runs on a schedule, because it needs credentials that pull requests from forks don’t get.

    Testing#

    The following tests cover the design:

    • Join behavior. The scheduled job re-runs the probes behind How the arithmetic join behaves, so a change in Datadog’s matching rules fails a check rather than a customer’s panel.
    • Two environments, one organization. Two environments with the same catalog ids send to one test organization, and each panel keeps them apart, with or without names.
    • Formula rewriting. A unit test renders a registry query with mzObjectName and asserts the hidden _info query and the formula factor, including a formula that already does arithmetic.
    • Tier list. The rendered metric-tiers.yaml names every _info family that an enrichment function reads.
    • The cluster stamp. helm-unittest asserts that the Datadog chain fills cluster only where it’s absent.
    • Parity. The ledger compares every Datadog dashboard’s manifest with its Grafana counterpart’s, and a fixture with an unlisted difference makes it fail.
    • Renders. Snapshot tests for each Datadog dashboard, as packages/dashboards/tests/ holds for the Grafana ones.
    • API acceptance. The scheduled job creates, reads back, and deletes every dashboard in a test organization.
    • Live data. Every ported datadogQuery returns data against a test install that sends to Datadog, and every joined panel returns the same series as its query without the join.

    Open questions#

    • What does the arithmetic join do at its edges? Settled by probing the query API on 2026-10-21. See How the arithmetic join behaves.
    • Can a template variable on the _info query’s name tag filter the joined result? Yes. A filter on a tag that only the _info query carries filters the panel.
    • Which ids does each _info family not cover? A joined panel loses their series. Transient collections, and environments older than the release that added mz_object_info, are the candidates to check.
    • Is the custom-metric cost of the _info series acceptable at the default tier, or do they belong in a tier an operator opts into?
    • Do names wait for all of DEP-349, or does the Datadog chain alias the few id labels the first set joins on ahead of it?
    • When are reference tables worth adding? Other ways to get names lists the conditions.
    • What duplication moves the panel list into a shared layer? Two or more dashboards whose manifests match panel for panel would be a clear signal, and the threshold is a judgment call.
    • Does CI get a Datadog test organization for the acceptance job and the live-data checks?
    • Which dashboards follow env-top? Field Engineering’s input, as DEP-115 asks.
