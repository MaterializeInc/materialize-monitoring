    Call-home#

    Call-home sends a reduced copy of your install’s telemetry to Materialize, so Materialize can see what’s running and what’s wrong without a support ticket. Your own Loki and Thanos keep the full copy, and nothing is sent unless you choose a call-home level. This page is for the operator of a materialize-monitoring install who decides whether to turn call-home on, and how much to send.

    One values key, callHome.level, chooses how much crosses. It defaults to off, which sends nothing. Each higher level sends everything the level below it sends, and more. The level builds a single destination, controlPlane, in pipeline.destinations, and changes nothing else. Bring Your Own Cloud stacks use the same levels. The only difference between the two is how the client certificate is issued, which happens outside this chart.

    Only your values raise the level. Nothing in the chart reads a level from Materialize.

    Call-home levels#

    The following table lists each level and what it sends:

    LevelWhat crosses
    offNothing. The default.
    heartbeatThe heartbeat: what your install runs, and whether its monitoring stack works.
    alertsThe heartbeat, and the alerts that are pending or firing (ALERTS).
    metricsMetrics at the essential tier, which holds the heartbeat and ALERTS.
    diagnosticsMetrics at the essential tier, and logs at WARN and above.

    profiles/call-home.values.yaml sets diagnostics, and nothing else.

    At diagnostics, the gateway sends at most 500 log lines per second per gateway replica, in bursts of at most 5000. It levels most lines, including Rust and Go panics, which arrive as CRITICAL. A line it can’t level is UNKNOWN, and no level sends those.

    The metric tiers are listed in Controlling what each destination stores.

    Turn on call-home#

    Before you begin, get a client certificate for your install from Materialize. Its URI SAN, spiffe://c.materialize.cloud/stack/CLIENT_STACK, is your install’s identity. The control plane reads your identity from the certificate, so the gateway sends no identity of its own.

    1. Create a kubernetes.io/tls Secret named mzmon-alloy-gateway-destination-tls in the gateway’s namespace:

      kubectl create secret tls mzmon-alloy-gateway-destination-tls \
  --namespace NAMESPACE --cert CERT_FILE --key KEY_FILE

      Replace the following:

      • NAMESPACE: the namespace the Alloy gateway runs in.
      • CERT_FILE and KEY_FILE: the certificate and private key Materialize issued.

      The gateway mounts the Secret at /etc/mzmon/destination-tls. At every level above off, the gateway fails to load its configuration without it, and names the missing file.

    2. Set the level.

      With Helm, add the profile to the -f list of your upgrade command, after the profiles you already use. To choose a level other than diagnostics, set callHome.level after it. The profiles ship inside the chart package; for more information, see Get the profiles.

      helm upgrade RELEASE oci://ghcr.io/materializeinc/helm-charts/materialize-monitoring \
  --version VERSION --namespace NAMESPACE \
  -f YOUR_VALUES.yaml \
  -f materialize-monitoring/profiles/call-home.values.yaml \
  --set callHome.level=metrics

      With the Terraform module, set callHome.level in additional_values.

    3. Confirm the gateway is sending. After the gateway restarts, the install notes show the level, and otelcol_exporter_sent_metric_points_total rises for component_id="otelcol.exporter.otlphttp.dest_controlPlane". At diagnostics, so does otelcol_exporter_sent_log_records_total.

    The certificate is re-read every five minutes, so a renewed certificate in the Secret is picked up without a restart.

    Credentials are redacted before anything is sent#

    At diagnostics, the gateway’s secret filter is on, whatever pipeline.logging.secretFilter.mode says. The gateway then replaces each credential it finds in a log line with <redacted:RULE_ID>, before it copies anything out of the line or sends it anywhere. Neither your own Loki nor the control plane’s copy holds a credential the filter caught. The level overrides shadow mode too, because shadow mode redacts only the copies it stores.

    Below diagnostics, no logs cross, and the mode is yours to set.

    The filter is an extra layer of protection, not the control: configure your components not to log credentials in the first place. For what the filter catches and what it costs, see Secret filtering.

    Send less than a level#

    To send less than your level, write an entry under pipeline.destinations.controlPlane in your own values file, after the profile. The level builds the destination, and your entry is applied over it. The following example sends errors and above from Materialize’s environments, at no more than 100 lines per second:

    pipeline:
  destinations:
    controlPlane:
      logs:
        minLevel: ERROR
        selector: '{namespace=~"environment-.+"}'
        rateLimit:
          rate: 100
          burst: 1000

    To send metrics and no logs, set pipeline.destinations.controlPlane.logs.enabled to false, or use the metrics level.

    The entry can also change the wire, such as url, tls, and queue. It can’t send more than the level. The render fails on any of the following:

    • A metrics.minMetricImportance wider than the level’s tier: heartbeat at heartbeat, alerts at alerts, and essential above.
    • Logs below diagnostics, a logs.minLevel below WARN, or logs.keepUnknown: true.
    • A logs.rateLimit.rate above 500, or a logs.rateLimit.burst above 5000.
    • A type other than otlp.

    Your own Loki and Thanos keep everything at every level.

    Turn off call-home#

    Remove the profile and any callHome.level you set, or set callHome.level to "off". Quote it: YAML reads a bare off as false, which the chart also accepts as off. The gateway stops sending at its next restart, which the upgrade triggers.

    At off, the render fails if pipeline.destinations.controlPlane is still in your values, unless it’s enabled: false. That way an entry written by hand, without a level, doesn’t stop sending silently.

    When the control plane is unreachable#

    The control plane’s copy is the only one that loses data. When the gateway can’t reach it, the destination’s queue fills and then drops entries, and delivery to your own Loki and Thanos continues. The drops are counted in otelcol_exporter_enqueue_failed_log_records_total and otelcol_exporter_enqueue_failed_metric_points_total.

    What the heartbeat sends#

    The heartbeat is a fixed record of what your install runs and whether its monitoring stack works. It carries no object names, query text, log lines, or other metric series. The heartbeat level sends the heartbeat and nothing else. The alerts level also sends ALERTS, and metrics and diagnostics send both alongside the essential tier. Any destination can send the same series with the metric tiers of the same names.

    The bundled Thanos ruler records the heartbeat every minute and writes it through the gateway, which is the path ALERTS takes. ALERTS holds a series only while an alert is pending or firing. A current heartbeat with no ALERTS means nothing is firing, and a missing heartbeat means the control plane can’t tell.

    The following table lists every series in the heartbeat:

    SeriesLabelsValue
    mzmon:heartbeatchart_version1
    mzmon:build_info:countcomponent, versionThe running processes of that component at that version. component is alloy, environmentd, kubelet, loki, node-exporter, postgres, or thanos.
    mzmon:node_uname_info:countmachine, releaseThe nodes with that CPU architecture and kernel release
    mzmon:environment_infoenvironment_id1 for each Materialize environment
    mzmon:cluster_created_timestamp_secondsNoneWhen the cluster’s kube-system namespace was created
    mzmon:rules:countNoneThe rules the Thanos ruler evaluates
    mzmon:rule_evaluation_failures:rate5mNoneFailed rule evaluations per second

    Each series also carries cluster, which is clusterName, and ruler_replica, the name of the ruler pod that wrote it. The gateway sets job and instance to thanos-ruler. A component that isn’t running reports no mzmon:build_info:count series.

    postgres is the PostgreSQL version of your Materialize metadata database, counted per database. It’s read through the postgres-exporter, because no cloud provider’s metrics carry an engine version. It covers each externalDependencies.consensus entry with flavor: postgres, whether the database runs on Amazon RDS, Cloud SQL, Azure Database for PostgreSQL, or a cluster of your own. Other databases the exporter watches aren’t reported.

    Your own Thanos stores the same series, so you can read exactly what the heartbeat sends:

    {__name__=~"mzmon:.+"}

    The heartbeat installs with the bundled Thanos and its monitoring, thanos.global.serviceMonitor.enabled. It needs rules.enabled, which is on by default. If you set a call-home level and the heartbeat doesn’t install, the render warns you, because the control plane can’t tell your install from one that went dark.

    Identity in the heartbeat#

    The heartbeat doesn’t name your company or your install. The control plane reads both from your client certificate. Each Materialize environment is named by its environment_id, the spec.environmentId UUID of its Materialize resource, and not by the resource’s name.

    mzmon:cluster_created_timestamp_seconds tells a rebuilt cluster from a copied one. A copy of a cluster, such as a staging cluster restored from production, keeps the original’s certificate and values, so it reports under the same identity. Both clusters report their own creation time, so the control plane sees two values under one identity. A rebuilt cluster reports a new value, and the old value stops.
